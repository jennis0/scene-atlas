# Security Evaluation — Scene Atlas (Hosted Mode)

**Scope**: Server mode (web server behind a reverse proxy)

## Deployment Model

Scene Atlas has three deployment modes:
1. **Electron desktop app** — backend runs as a local sidecar; the OS user boundary provides isolation.
2. **Web server behind a reverse proxy** — this document evaluates this mode.
3. **Developer mode** — localhost only, no security expectations.

## Server mode has no built-in authentication

The backend has no authentication or authorisation. Every API endpoint, including uploads, deletion of the whole library and settings changes, is available to anyone who can reach the server. There is no token or bearer-auth support in the code.

Server mode must therefore only be exposed behind a reverse proxy that authenticates every request — HTTP basic auth, forward-auth (e.g. Authelia, Authentik), an OAuth proxy (e.g. oauth2-proxy), or an access gateway such as Cloudflare Access or Tailscale. Never expose the backend port directly to the internet. Because the frontend loads images with plain `<img src>` requests, the proxy must authenticate with a mechanism the browser sends automatically (cookies or basic auth), not a header the app would have to add.

## What's Already Done Well

| Area | Details |
|------|---------|
| SQL injection | Queries use the SQLAlchemy ORM; FTS5 input is sanitised in `fts_service.py` |
| XSS | No unsafe DOM injection; content rendered via React text interpolation |

| Error handling | Global handler returns a generic 500; details logged server-side |
| Secrets | No hardcoded secrets; config via env vars; `.env` is git-ignored |
| Supply chain | Lock files (`uv.lock`, `package-lock.json`) committed |
| CSP | Restrictive Content-Security-Policy meta tag in `frontend/index.html` |
| Pre-commit | Husky + lint-staged runs ruff, ESLint and Prettier |
| Code safety | No shell invocation or dynamic code execution in the backend |
| Container user | The Docker image runs as an unprivileged `app` user (`SCENE_ATLAS_UID`/`SCENE_ATLAS_GID`, default 1000) with the venv on `PATH`; only `/app/data` and `/app/images` are writable by it |

## Findings

### 1. CRITICAL: No Authentication or Authorization

**Status**: Open. Mitigated only by deployment (see above).

Bearer-token auth was prototyped and abandoned: a token baked into the frontend bundle gives no protection against anyone who can load the frontend. The planned approach is session-based auth (login page, HTTP-only session cookies, CSRF protection), which also covers `<img src>` requests. Until then, authentication is the reverse proxy's job.

### 2. HIGH: Path Traversal in Uploads

**Status**: Fixed.

Staging is per job: `{SCENE_ATLAS_DATA_DIR}/staging/{job_id}/{staging_key}`. `staging_key` is generated by the server (`uuid4().hex` + the lower-cased extension) and stored on `ImportItem.staging_key`. The client-supplied `relative_path` is normalised and used only for display, group planning and resume matching. Uploads go to `PUT /imports/{job_id}/items/{item_id}/content`, addressed by database ids; archive members get their own server-generated keys. See [storage.md](storage.md#staging).

### 3. HIGH: Rate Limiting

**Status**: Done.

`slowapi`, keyed on the client address (`request.client.host`), with two tiers:

- **expensive** (`SCENE_ATLAS_RATE_LIMIT_EXPENSIVE`, default `2/minute`): `POST /search/rebuild-embeddings`, `POST /library/metadata-export`, `PATCH /settings/`, `POST /tags/retag-all`, `POST /tags/packs/{name}/import`, `POST /images/backfill-grids`
- **destructive** (`SCENE_ATLAS_RATE_LIMIT_DESTRUCTIVE`, default `1/minute`): `DELETE /system/library`, `POST /system/tags/reset`

`SCENE_ATLAS_RATE_LIMIT_ENABLED=false` disables it.

Import endpoints are not rate limited: a single import makes one request per file (≈10k for a 10k-file import), so a per-IP limit would throttle legitimate imports. Per-file uploads (`PUT …/items/{item_id}/content`) are bounded by `max_import_file_size` (413 on the streamed body) and require an existing item awaiting bytes; they do not take the heavy-op semaphore. Jobs are capped at `SCENE_ATLAS_MAX_IMPORT_ITEMS` files and seal checks free disk space. Archive upload and seal are gated by the heavy-op semaphore (`acquire_heavy_op`, see [resource-management.md](resource-management.md)). The client retries 429/5xx up to 5 times per file, then records a resumable local failure, so reverse proxies with their own rate limits must allow for the per-file request volume.

**Client address behind a reverse proxy**: `main.py` installs uvicorn's `ProxyHeadersMiddleware` as the outermost middleware, trusting only `SCENE_ATLAS_FORWARDED_ALLOW_IPS` (default `127.0.0.1,::1`). For a connection from a trusted address it replaces the client address with the rightmost `X-Forwarded-For` entry that is not itself trusted (and takes the scheme from `X-Forwarded-Proto`); from anywhere else both headers are ignored, so a client cannot pick its own rate-limit bucket. A proxy that appends to the header is therefore as safe as one that overwrites it. The setting is read by the app (so it works from `.env`), and the launch paths we ship (`Dockerfile`, `scripts/app/start.py`, `main.py`'s `__main__`, the sidecar) pass `--no-proxy-headers` / `proxy_headers=False` so uvicorn's own copy of the middleware, which reads `SCENE_ATLAS_FORWARDED_ALLOW_IPS` only from the process environment and defaults to `127.0.0.1`, can't apply a different list. If the proxy is not in the list, nothing breaks but every client shares the proxy's bucket. In Docker the proxy's connections come from the Docker network, not loopback, so the operator must set it (see [docs/deploy/server.md](../docs/deploy/server.md#client-ip-addresses-and-rate-limits)). Tests: `backend/tests/integration/test_proxy_headers.py`.

### 4. MEDIUM: Security Headers

**Status**: Done.

A pure ASGI `SecurityHeadersMiddleware` adds `X-Content-Type-Options: nosniff`, `X-Frame-Options: DENY`, `Referrer-Policy: strict-origin-when-cross-origin` and `Permissions-Policy: camera=(), microphone=()` to every response. HSTS is omitted on purpose: it must come from the TLS-terminating proxy so non-TLS deployments (Electron, local dev) keep working.

### 5. MEDIUM: Security Scanning in CI

**Status**: Done (October 2026).

The `backend-security` job in `.github/workflows/ci.yml` (pull requests only) runs, and fails the PR on any finding that is not listed under [Accepted scanner findings](#accepted-scanner-findings):

- `pip-audit --desc` over the `dev` + `cpu` environment (Python CVE scan; accepted IDs are passed as `--ignore-vuln` with a comment)
- `bandit -r backend/app backend/pipeline -ll` (Python SAST, medium severity and up; accepted findings carry an inline `# nosec BXXX` with a reason)

The `frontend-build` job runs `npm audit --omit=dev --audit-level=high` on `frontend/`, so a high or critical advisory in a dependency that ships in the bundle fails the PR. Dev and build tooling (frontend dev deps, the root Electron/electron-builder tree, `docs/`) is not gated; it is kept clean through Dependabot and periodic lockfile refreshes, and what cannot be fixed is listed below.

pip-audit and npm audit query live advisory databases, so a new advisory can turn a PR red without a code change. That is intended: fix it (usually `uv lock --upgrade-package <pkg>` or a targeted `npm update <pkg>`), or add it to the accepted list below with a reason.

### 6. MEDIUM: Electron IPC choosing the library's folders

**Status**: Partially mitigated.

The renderer can call `library:apply` (exposed as `window.electronAPI.applyLibrary`) with the app data, store and linked folders ([library-setup.md](library-setup.md)). The main process (`electron/src/main.ts`) writes them to the app config and restarts the backend on them. Current checks:

- The handler is registered with `handleTrusted`, which rejects calls whose sender frame is not an app URL (the backend sidecar origin, `file:` for `loading.html`, or the dev server in development).
- Every path must be absolute. The store and app data may not be, or contain, the linked folder (`parseLibraryDirs`), and the backend's startup check repeats that rule.
- The app data and store folders are created if needed and must pass a write test. The linked folder is never created or written.
- Only empty first-launch (provisional) folders are ever deleted, and only when they hold nothing Scene Atlas didn't create.

There is no restriction on which absolute paths are accepted, so code running in the renderer could point the backend at any writable location. Renderer windows run with `contextIsolation`, `sandbox` and no `nodeIntegration`, and navigation away from app URLs is blocked, which limits who can reach the channel.

### 6a. MEDIUM: Local imports read paths named by the client

**Status**: Mitigated.

`POST /imports/{id}/local-sources` lists and reads files at paths the client sends ([local-ingest.md](local-ingest.md#6-security)). Controls:

- Desktop app only: the route returns 404 unless `SCENE_ATLAS_APP_MODE=app`, where the sidecar binds `127.0.0.1` and any caller is already a local process running as the user.
- DNS rebinding: in app mode `LoopbackHostMiddleware` (`backend/app/host_check.py`) rejects requests whose `Host` isn't `127.0.0.1`, `localhost` or `[::1]` (400), so a rebound web page can't reach this or any other endpoint.
- Only media is ingested: each file passes the magic-byte check (`verify_media_mime`) before it's copied; symlinks aren't followed; sources are never written.

### 6b. MEDIUM: Library inspection reads paths named by the client

**Status**: Mitigated.

`POST /library/inspect` ([library-setup.md](library-setup.md#34-post-libraryinspect-desktop-only)) looks at folders the setup wizard names: it reads library markers, opens `battlemap.db` read-only, and walks a folder to count images. Controls:

- Desktop app only (404 unless `SCENE_ATLAS_APP_MODE=app`), behind the loopback `Host` check, like `local-sources` (6a).
- Read-only: nothing is created or changed, except that SQLite may leave `-wal`/`-shm` files beside a database it opened read-only.
- Returns an outcome, counts, library IDs and the library's own folder hints; never file names. Paths must be absolute.
- The folders themselves are never set through the API: they reach the backend only as sidecar arguments or env vars.
- Admission-controlled (`acquire_heavy_op`), since counting a large folder takes seconds.

### 6b-1. LOW: Downloads

`POST /downloads` ([export-backup-move.md §5](export-backup-move.md#5-export-groups)) streams the chosen groups' originals as a zip. It is a form POST, a request any site can send, so it refuses one another site sent: `Sec-Fetch-Site` must be `same-origin` (or `none`), or, from a browser that doesn't send it, `Origin` must match `Host`. A request with neither header comes from no browser (a browser sends `Origin` with every cross-origin POST), so it can't be another site's page, and is allowed. Behind a proxy, `Host` must be passed through (`proxy_set_header Host $host`) for the `Origin` comparison. Ids are numbers only; the selection is capped (999 files, 2 GB, 10,000 ids). Not rate-limited: the caps bound a download's cost. Its error responses are plain text and may be framed by the app's own origin (`X-Frame-Options: SAMEORIGIN`), so the app can show them; every other response keeps `DENY`. Files are read through `originals.original_path`, so the linked folder's containment check applies; zip member names come from `ReadableLayout`, never from stored paths. `POST /downloads/check` takes JSON and only counts.

### 6b-2. LOW: Metadata export

`POST /library/metadata-export` ([export-backup-move.md §4](export-backup-move.md#4-export-metadata)) starts a background export. Controls:

- **A JSON body**, so a page on another site can't start one: a cross-origin JSON POST needs a CORS preflight, which only configured origins pass. Rate-limited as expensive; one export at a time (409).
- **A path only in the desktop app** (`app_mode == "app"`; 422 on servers): it must be absolute, in an existing folder, not a folder itself, and not inside the library's own folders (app data, the store, the linked library: `library_identity.inside_any`), so an export can't replace the live database. On a server the file goes to `{SCENE_ATLAS_DATA_DIR}/exports/` under a name the server makes.
- **`GET /library/metadata-export`** reports the running export's job id and the newest finished file's name, nothing else.
- **Served back by name only**: `GET /library/metadata-export/{name}` serves a file from that folder only if the name matches the pattern the server writes (`scene-atlas-metadata-<date>-<time>.jsonl.gz`), so no other file can be named. The name is matched in full (`fullmatch`, ASCII digits). Exports are deleted after 24 hours (an hourly task), and partial files at startup.
- The export holds the library's metadata and settings, not secrets: there are none in `app_settings`. Server mode's lack of authentication applies as to every other endpoint.

### 6b-3. LOW: Metadata in an import

A `scene-atlas.jsonl` in an import ([export-backup-move.md §6](export-backup-move.md#6-import)) is untrusted: it goes through the lenient reader, its paths are only compared with file names (never opened), a recorded filename is reduced to a plain name with the file's own extension (`ingest_process.restored_filename`), text is cut to the API's limits, and a file that fails validation is ignored. It is applied only to files whose bytes hash to one of its entries. **A file can name any group `uid`**: an image imported with it joins the library's group with that uid, if there is one. Uids are random and not shown in the UI, so naming one needs a copy of an export from this library; whoever can import can already edit groups through the API, so this grants nothing new.

### 6b-4. MEDIUM: Rebuild from export

`/library/rebuild` ([export-backup-move.md §8](export-backup-move.md#8-rebuild)) replaces the library's metadata, and `POST /apply` stops a server. Controls: the POSTs (check, build, apply) require a JSON body and the upload is a PUT, so a cross-origin page can't send any of them without a CORS preflight; the upload is under the import size limit; apply refuses if the library changed since the check; check and build are rate-limited as expensive and apply as destructive, and nothing changes the live library until apply. The file is untrusted: it's read by the lenient reader, and nothing in it is used as a path (storage keys are looked up through `ImageStore`, linked paths only checked with `is_file`, and only when they resolve inside the configured folder). The previous database is kept in `rebuild/old-<id>/`. As for every endpoint, server mode has no authentication: anyone who can reach it can rebuild, as they can already purge.

### 6b-5. LOW: Move library

`/library/move` is desktop-only (404 on servers). Its targets are checked like the library folders (absolute, outside and not containing them); the copy writes only under the target. `DELETE /library/move/old` deletes only the folders recorded in `app_settings.moved_from` that hold the note a finished move wrote and are not, and don't contain, a folder in use.

### 6c. MEDIUM: Reading the linked folder

**Status**: Mitigated.

The linked folder ([library-setup.md §4](library-setup.md#4-linked-library)) is the first place where a path stored in the database (`source_files.rel_key`) reaches the filesystem. Controls:

- **Configuration only.** The folder comes from `SCENE_ATLAS_LINKED_LIBRARY_DIR` or the desktop app's `--linked-library-dir` sidecar argument; no endpoint sets it. `POST /library/scan` names no path. On servers no response carries the folder's path: status and waiting imports give its name.
- **Containment check** on every read (`originals.LinkedFolder.local_path`): the key must be relative with no `..`; joined to the root, it must resolve (`Path.resolve`) inside the resolved root (case-normalised), to a regular file that isn't a symlink (`lstat`). Anything else is refused as missing and logged. Keys come from the scan's walk, which doesn't follow symlinks, so the check is a second line.
- **Read-only by type.** `LinkedFolder` has no `put` or `delete`; images read from the folder have no `storage_key`, so deletion, purge and the orphan sweep (which only walk the store's shard folders) can't reach its files. The store and app data may not be or contain the folder (startup check), so purge can't empty it either.
- **One interface.** File serving, group download, export and the backfills read originals only through `originals.original_path`; the worker resolves linked items through the same check rather than their stored absolute `source_path`.
- **Server deployments** are documented with a read-only mount (`-v /srv/maps:/library:ro`), so even a bug can't write to the folder.

Accepted: a file swapped for a symlink between the check and the read (a TOCTOU window) could be followed. That needs write access to the user's own maps folder, which already implies control of the files being served.

### 7. MEDIUM: CORS Configuration

**Status**: Done.

A warning is logged at startup when `SCENE_ATLAS_APP_MODE=server` and `SCENE_ATLAS_CORS_ORIGINS` is still the localhost default.

### 8. LOW: CSP `connect-src` Too Broad

**Status**: Done.

Electron loads the UI from the backend sidecar, so the frontend is always same-origin with the API and the CSP in `frontend/index.html` uses `connect-src 'self'` in every mode.

### 9. LOW: No CSRF Protection

**Status**: Open; to be implemented with session-based auth. Not exploitable while there are no credentials to ride on, but becomes relevant if the proxy uses cookie-based auth.
